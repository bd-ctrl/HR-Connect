# เชื่อมคะแนน CUBIC CONNECT กับ Base

สถานะ: ซอร์ส Worker และหน้า GitHub Pages พร้อมทดสอบร่วมกัน ยังต้องนำ Worker ไป Deploy ในบัญชี Cloudflare ของผู้ดูแล และทดสอบกับ Base จริง

รายชื่อผู้ร่วมงานอ่านจากคอลัมน์ชื่อเล่นและแผนกในทะเบียนพนักงาน (`LARK_TABLE_ID`) ผ่าน `/employees` แยกจากตารางคะแนน (`LARK_SCORE_TABLE_ID`) รายชื่อยังแสดงได้เมื่อระบบคะแนนยังไม่พร้อม และเริ่มกรอกแบบประเมินเป็นร่างได้เมื่อเลือกแผนกกับคนครบ การส่งจริงยังต้องเตรียมตารางคะแนนและตรวจใบตอบรับครบ 3 ด้าน

ลำดับการส่งที่ต้องรักษา: พนักงานกดส่ง → Worker บันทึกคำตอบครบ 3 ด้านลงตารางคะแนน Lark → ยืนยันผลบันทึกให้หน้าเว็บ → HR อ่านรายการจากตารางคะแนนนั้น คะแนน 1–3 บันทึกสถานะรอ HR ตรวจสอบตั้งแต่การส่งครั้งแรก ส่วน 4–5 บันทึกสถานะผ่านอัตโนมัติ HR ไม่ต้องอนุมัติก่อนให้ข้อมูลเข้าตาราง และร่างในเครื่องยังไม่ถือเป็นผลที่ส่งแล้ว

## ตั้งค่าที่เพิ่มจากระบบล็อกอินเดิม

- `LARK_SCORE_TABLE_ID`: รหัสตารางคะแนน `tblwPkR2PylXNoM1` ส่วน `LARK_TABLE_ID` เดิมยังใช้ทะเบียนพนักงาน
- `SCORE_STORAGE_PRIVATE`: ตั้งเป็น `true` **หลังจำกัดการแชร์ Base ให้เฉพาะ HR และแอปแล้ว** ค่านี้เป็นคำยืนยันของผู้ดูแล ไม่ได้แก้สิทธิ์ Lark แทนผู้ดูแล
- `EVALUATION_ROUND`: ไม่บังคับ ค่าเริ่มต้น `2026-10` เพื่อให้ตรงกับรอบเดิม
- `ROUND_STATE`: ไม่บังคับ ค่าเริ่มต้น `open`; เปลี่ยนเป็น `review` หรือ `released` เพื่อปิดรับการส่งใหม่
- `MIN_RATERS`: ใช้กับค่าเฉลี่ยเท่านั้น ไม่บล็อกรายการคะแนน 4–5 ที่ผู้รับเห็นทันที ไม่บังคับ ค่าเริ่มต้น `3` ตามกติกาเดิม เปลี่ยนเฉพาะเมื่อมีนโยบายอนุมัติใหม่ และเริ่มรอบใหม่ ผลที่บันทึกแล้วคงเกณฑ์ของเวอร์ชันเดิม
- `FIELD_ROLE`: ค่าเริ่มต้น `Role` ในทะเบียนพนักงาน รหัสแอดมินที่ยืนยันแล้วและมีทั้งค่า `Admin` กับ `User` จะเปิดหน้าจอเลือกบทบาท Worker ตรวจสิทธิ์อีกครั้งตอนเรียก API
- `FIELD_EMPLOYEE_ID`: ไม่บังคับ ถ้าไม่ตั้ง HR ใช้รหัสเต็มในคอลัมน์เลขบัตรประชาชนตามทะเบียนปัจจุบัน ถ้าตั้งจะค้นรหัสพนักงาน 8 หลักในคอลัมน์นี้
- `DRAFTS_DB`: D1 database binding สำหรับร่างประเมินตามบัญชี

ตัวแปรและ Secret ของล็อกอินเดิมใช้ต่อได้ทั้งหมด ไม่ใส่ App Secret ในไฟล์หรือ GitHub

## นำขึ้นใช้งาน

1. ใน Lark Developer ให้แอป HR CONNECT มีสิทธิ์ `bitable:app` แบบ Tenant token และเผยแพร่เวอร์ชันเมื่อระบบร้องขอ แอปต้องมีสิทธิ์แก้ไข Base ด้วย
2. จำกัดการแชร์ Base: ทะเบียนและเหตุผลประเมินต้องไม่เปิดอ่านได้จากลิงก์สาธารณะ พนักงานใช้งานผ่านเว็บไซต์ ไม่จำเป็นต้องได้รับสิทธิ์เปิด Base
3. เพิ่ม `SCORE_STORAGE_PRIVATE=true` ใน Cloudflare หลังตรวจสิทธิ์เรียบร้อย
4. เปิด Workers & Pages → cubic-connect-api → Edit code แล้วแทนที่ worker.js ทั้งไฟล์ด้วย **worker.mjs** ในโฟลเดอร์นี้ จากนั้นกด Deploy
5. ตรวจคอลัมน์ในเมนู **เชื่อมต่อ Base** ของ HR Admin หากมีคอลัมน์ขาด ให้กด **เตรียมตารางคะแนน**
6. ปุ่มนี้เพิ่มเฉพาะคอลัมน์ที่ขาดและตัวเลือกที่ใช้ในคอลัมน์เดิม ไม่ลบแถว ไม่เปลี่ยนชนิดคอลัมน์เดิม ถ้าชนิดเดิมไม่รองรับ หน้าผู้ดูแลจะแสดงชื่อคอลัมน์ และ Worker จะหยุดก่อนเพิ่มคอลัมน์ใด ๆ ให้เทียบโครงสร้างจริงกับการจับคู่ในโค้ดก่อน ระบบจะอ่านคอลัมน์กลับมาตรวจครบก่อนยืนยันการเตรียมสำเร็จ
7. ออกจากระบบและเข้าสู่บัญชีพนักงาน ส่งผลใหม่หนึ่งชุด ตรวจว่า Base มี 3 แถว จากนั้นเข้าบัญชีผู้รับเพื่อตรวจสถานะและคะแนน

### ผู้รับผิดชอบ 1–2–3

1. **ผู้พัฒนา:** แก้และทดสอบ Worker กับหน้าเว็บ พร้อมอัปเดต GitHub การทดสอบใช้ข้อมูลจำลอง ยังไม่ใช่การทดสอบบันทึกจริง
2. **ผู้ดูแล Cloudflare:** เปิด Workers & Pages → cubic-connect-api → Edit code คัดลอก `worker-for-cloudflare.txt` ทั้งไฟล์แทนโค้ดเดิม แล้ว Deploy ใช้ตัวแปรและ Secret ของระบบเดิม การอัปเดต GitHub ไม่ได้ Deploy Worker ภายนอกแทนขั้นตอนนี้
3. **ผู้ทดสอบ:** ใช้บัญชีพนักงานส่ง 1 ชุด → ตรวจ Base ครบ 3 แถว → ผู้รับเห็นด้านที่ได้ 4–5 ทันที → ผู้ส่งเห็นชื่อผู้รับในประวัติ โดยไม่ต้องล็อกอิน HR ก่อน ส่วน HR เข้ามาเมื่อต้องตรวจคะแนน 1–3 การเตรียมคอลัมน์เป็นงานติดตั้งครั้งแรก

ถ้าขึ้นคอลัมน์ที่ชนิดข้อมูลไม่รองรับ ให้ผู้พัฒนาตรวจชื่อและชนิดของคอลัมน์นั้นกับตารางจริงก่อน ไม่เปลี่ยนหรือลบคอลัมน์ที่มีข้อมูลเพื่อให้ผ่านการตรวจ การเผยแพร่หน้าเว็บสำเร็จหรือเตรียมตารางสำเร็จยังไม่ใช่หลักฐานว่าการส่งคะแนนจริงทำงานครบวงจร

### เตรียมคอลัมน์ใน Lark โดยตรง

ผู้ดูแล Base สามารถเพิ่มคอลัมน์ต่อไปนี้ในตารางคะแนนเดิม `tblwPkR2PylXNoM1` ได้โดยตรง แทนการใช้ปุ่มเตรียมตารางคะแนน เพิ่มเฉพาะชื่อที่ยังไม่มี ไม่สร้างตารางใหม่และไม่ลบข้อมูลเดิม

| ชื่อคอลัมน์ที่โค้ดใช้ | ชนิดข้อมูล |
|---|---|
| `CC_รหัสผู้รับ` | ข้อความ |
| `CC_รหัสผู้ประเมิน` | ข้อความ |
| `CC_โปรเจกต์` | ข้อความ |
| `CC_ข้อมูลยืนยัน` | ข้อความ |
| `CC_รหัสผู้ตรวจสอบ` | ข้อความ |
| `วันที่ประเมิน` | วันที่และเวลา |

จากนั้นตรวจใน Cloudflare ว่า `LARK_SCORE_TABLE_ID` ชี้มาที่ตารางนี้ และจำกัดการแชร์ Base ให้เฉพาะผู้มีสิทธิ์ก่อนยืนยัน `SCORE_STORAGE_PRIVATE=true` ตัวแปรนี้ไม่ได้เปลี่ยนการแชร์ใน Lark ให้เอง ทดสอบส่งผลหนึ่งชุดที่ได้รับอนุญาตและตรวจว่ามี 3 แถวใน Base ก่อนตรวจคิว HR

หน้าพนักงานใช้ข้อความส่งไม่สำเร็จแบบสั้นและเก็บร่างไว้ รายละเอียดคอลัมน์ การตั้งค่า และปุ่มตรวจการเชื่อมต่ออยู่ฝั่ง HR Admin

## หากวางโค้ดแล้วเกิด SyntaxError

`Illegal return statement` หมายถึงมี `return` อยู่นอกฟังก์ชัน ส่วน `Invalid regular expression: missing / at worker.js:1` ชี้ว่าตัวแปล JavaScript พบ regular expression ที่ไม่สมบูรณ์ที่บรรทัดแรก ให้ตรวจเนื้อหาที่วางใน editor โดยตรง ซอร์สที่ตรวจไวยากรณ์ผ่านจะเริ่มด้วย `const LARK_API` และไม่มีข้อความหรือคอมเมนต์นำหน้า

1. ดาวน์โหลด [worker-for-cloudflare.txt](./worker-for-cloudflare.txt) แล้วเปิดด้วย Notepad หรือโปรแกรมแก้ไขข้อความ ไฟล์นี้เป็นสำเนาเต็มของ `worker.mjs` สำหรับคัดลอก ไม่ต้องกรอก Secret ลงในไฟล์
2. ในไฟล์ข้อความ กด Ctrl+A แล้ว Ctrl+C จากนั้นคลิกในช่องโค้ด `worker.js` ของ Cloudflare กด Ctrl+A แล้ว Ctrl+V เพื่อแทนที่ทั้งไฟล์
3. กด Ctrl+Home ในช่องโค้ด ตรวจว่าบรรทัดแรกเป็น `const LARK_API = "https://open.larksuite.com/open-apis";` และช่วงท้ายมี `export default {` พร้อมฟังก์ชัน `async fetch(request,env)` อย่าคัดลอกเฉพาะฟังก์ชันคะแนนหรือเครื่องหมาย ``` จากข้อความแชต
4. กด Deploy แล้วเปิด `https://cubic-connect-api.ba-bd5.workers.dev/health` ตรวจว่าได้ `"ok":true` และ `"version":"scores-v2"`

`worker.mjs` เป็นไฟล์ต้นฉบับ เมื่อแก้ซอร์สในอนาคตให้สร้าง `worker-for-cloudflare.txt` ใหม่จากไฟล์นั้นทั้งไฟล์ เพื่อให้สำเนาสำหรับคัดลอกตรงกับรุ่นล่าสุด

## คะแนนปรากฏเมื่อใด

- ผลที่ส่งใหม่ทุกคะแนนบันทึกครบ 3 ด้านลง Base ก่อนยืนยันสำเร็จ โดยผูกผู้รับด้วย record ID ไม่ใช้ชื่อในการจับคู่ ไม่มีเงื่อนไขว่า HR ต้องล็อกอินก่อน
- คะแนน 4–5 ผ่านอัตโนมัติ ผู้รับเห็นรายการรายด้านพร้อมวันที่จาก `/me/state.feedback` ทันทีหลังบันทึกครบ ไม่รอ HR หรือผู้ประเมินครบ 3 คน คะแนน 1–3 ต้องมีเหตุผลและถูกเก็บใน Base ทันที แต่จะปรากฏให้ผู้รับหลัง HR อนุมัติเท่านั้น
- ค่าเฉลี่ยแต่ละด้านยังต้องมีผู้ประเมินอย่างน้อย 3 คนตามกติกาเดิม จึงแยกจากรายการคะแนนที่ผู้รับเห็นทันที หน้าเว็บตรวจข้อมูลใหม่อัตโนมัติทุก 15 วินาทีเมื่อเปิดอยู่ และเมื่อกลับเข้าแท็บ ไม่ใช้ข้อความโหลดคะแนนผิดพลาดหรือปุ่มโหลดเองบนหน้าพนักงาน
- ค่าเฉลี่ยรวมเป็นค่าเฉลี่ยเท่ากันของ 3 ด้านที่แสดงได้ หากด้านใดยังไม่ครบเกณฑ์จะแสดงสถานะรอโดยไม่สร้างคะแนนขึ้นเอง
- ผลถูก Reject ไม่รวมในการคำนวณ และไม่ส่งผลตัดสินหรือหมายเหตุ HR ไปให้ผู้รับ
- ผู้รับอ่านได้เฉพาะคะแนนที่แสดงได้ของตัวเองและค่าเฉลี่ยที่ครบเกณฑ์ ไม่ได้รับชื่อ/รหัสผู้ประเมิน รหัสแบบประเมิน เหตุผลดิบ โปรเจกต์ หรือหมายเหตุ HR การแสดงคะแนนทันทีไม่รับรองว่าผู้รับจะอนุมานผู้ส่งจากเวลาไม่ได้
- แจ้งเตือนเฉพาะผลที่แสดงได้ใน 30 วันล่าสุด ไม่แจ้งคะแนน 1–3 ที่ยังรอตรวจหรือถูก Reject และไม่แสดงปุ่มโหลดคะแนนแก่พนักงาน
- ผู้ส่งเห็นผู้รับและวันที่ในประวัติทันทีหลังบันทึกครบ 3 ด้าน ทั้งคะแนนสูงและคะแนนที่รอ HR โดยใช้ข้อมูลยืนยันจาก Base เท่านั้น ใบตอบรับมี `history_entry` เพื่อเก็บประวัติในหน่วยความจำของบัญชีปัจจุบันเมื่อการอ่านรอบถัดไปล้มเหลว ล้างเมื่อออกจากระบบ ไม่สร้างประวัติจากร่างหรือรายการที่ส่งไม่ครบ

## เปิดบันทึกร่างข้ามอุปกรณ์

1. สร้าง D1 database ชื่อ `cubic-connect-drafts` ในบัญชี Cloudflare เดียวกับ Worker
2. เปิด **Workers & Pages → cubic-connect-api → Bindings → Add binding → D1 database** ตั้งชื่อตัวแปร `DRAFTS_DB` และเลือกฐานข้อมูลที่สร้าง
3. ตรวจ `/health` ว่ามี `account-drafts` ใน capabilities ตารางร่างจะสร้างเมื่อเรียกใช้ครั้งแรก
4. บันทึกร่าง แล้วใช้บัญชีเดิมเปิดแบบประเมินของผู้รับคนเดิมในรอบเดียวกันบนอีกอุปกรณ์ ร่างเก่าในเครื่องจะซิงก์เมื่อกดบันทึก

การยืนยันส่งยังบันทึกผลลง Lark Base ร่างใช้ฐานข้อมูลแยกตามบัญชี รอบ และผู้รับ หากสองเครื่องแก้ร่างเดียวกัน ระบบจะให้เลือกฉบับก่อนบันทึกทับ

## ความถูกต้องและขอบเขต

- Worker ตรวจ session, สถานะพนักงาน, บทบาท HR, คะแนน/เหตุผล, การประเมินตัวเอง และรอบที่เปิดรับฝั่งเซิร์ฟเวอร์
- ใช้รหัสแบบประเมินจากรอบ/ผู้ประเมิน/ผู้รับ พร้อม `client_token` สำหรับการสร้างคำตอบแต่ละด้าน การส่งซ้ำไม่เขียนทับคะแนนเดิม
- ถ้าส่งไม่ครบ 3 ด้านหรือข้อมูลขัดกัน จะไม่แสดงเป็นผลสำเร็จและไม่นำชุดนั้นไปคำนวณ การส่งซ้ำด้วยข้อมูลเดิมพยายามบันทึกเฉพาะด้านที่ยังขาด
- Base ไม่มี unique constraint แบบฐานข้อมูล SQL โค้ดจึงตรวจและรวมหนึ่งชุดต่อผู้ประเมิน/ผู้รับ/รอบอีกครั้งก่อนคำนวณ แถวซ้ำไม่เพิ่มน้ำหนักคะแนน แถวขัดกันถูกระงับจากผล
- ข้อมูลต่อคำขอมีขอบเขต 10,000 แถวและตรวจ pagination ถ้าเกินจะแจ้งข้อผิดพลาดแทนแสดงข้อมูลบางส่วน
- การล็อกอินยังคงรูปแบบตรวจเลขจากทะเบียนเดิม เลขบัตรอย่างเดียวไม่พิสูจน์เจ้าของบัญชี ควรเพิ่มการยืนยันตัวตนก่อนเปิดใช้วงกว้าง ระบบนี้ไม่อ้างว่าปกปิดตัวตนจากผู้ดูแล Base ได้
- คิว HR นับรายการรออนุมัติรายด้าน การอนุมัติบันทึกผู้ตรวจสอบและเวลา การไม่อนุมัติต้องระบุเหตุผล
- Heatmap สรุปคะแนนที่แสดงได้ตามแผนกผู้รับและด้านประเมิน ใช้น้ำหนักผู้ประเมินแต่ละคนเท่ากัน และแสดงตัวเลขเมื่อมีผู้ประเมินครบเกณฑ์

## ตรวจสอบโค้ด

รัน `node cloudflare/worker-test.mjs` และ `node directory-ui-test.mjs` จากราก repository ใช้ข้อมูลสมมติเท่านั้น ไม่ส่งข้อมูลจริงเข้า Base

## ประวัติที่ผู้ส่งเห็นครบทั้งสามด้าน

`/me/state` และผลตอบกลับหลังส่งสำเร็จ เพิ่ม `history[].answers` / `history_entry.answers` เป็นรายการ `dimension`, `score`, `reason` ครบสามด้าน พร้อม `context` ของงาน ข้อมูลนี้มาจากสามแถวที่บันทึกครบใน Base แล้ว และส่งเฉพาะเจ้าของประวัติตาม session ฝั่งเซิร์ฟเวอร์ รวมคะแนน 1–3 ที่ตนเองส่งและกำลังรอ HR ด้วย ไม่เปลี่ยนข้อมูลที่ผู้รับมองเห็น และไม่เปิดชื่อผู้ประเมินในผลของผู้รับ

ต้องเผยแพร่ Worker จาก `worker-for-cloudflare.txt` รุ่นนี้ให้สำเร็จจึงอ่านรายละเอียดของประวัติเดิมและอ่านข้ามอุปกรณ์ได้ ตรวจ `/health` ว่า `capabilities` มี `sent-history-details` ไม่มีคอลัมน์ Base หรือตัวแปรใหม่ที่ต้องเพิ่มสำหรับการเปลี่ยนแปลงนี้

เมื่อ API รุ่นเดิมส่งเฉพาะชื่อและวันที่ หน้าเว็บแสดงเฉพาะข้อมูลที่ได้รับ ผลที่เพิ่งส่งจะแสดงคะแนนในเซสชันหลังได้รับใบยืนยันว่าบันทึกครบสามด้านแล้ว
